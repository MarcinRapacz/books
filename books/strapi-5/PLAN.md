## Zakres rozdziałów

1. **Architektura i droga żądania.** Czym Strapi jest pod spodem (Koa, warstwy). Struktura projektu (`config/`, `src/api/<name>/{content-types,controllers,services,routes,policies,middlewares}`, `src/components`, `src/extensions`, `src/plugins`, `src/index.ts`, `types/generated`). Droga żądania jako diagram: globalne middleware → router → uwierzytelnienie i autoryzacja → polityki → middleware trasy → kontroler → serwis → Document Service (+ jego middleware) → Query Engine → baza; które warstwy dotyczą Content API, a które panelu admina. Content API vs Admin API. Funkcje `register`/`bootstrap`/`destroy` (co wolno w której). Konfiguracja: pliki `config/*.ts`, `env()` z rzutowaniem, konfiguracja per środowisko (`config/env/production/*`), dostęp `strapi.config.get`. Obiekt `strapi` i getterzy (`strapi.service()`, `strapi.documents()`, `strapi.plugin()`), UID-y (`api::article.article`). CLI do introspekcji (`routes:list`, `policies:list`, `middlewares:list`, `content-types:list`, `console`). Mapa: „gdzie umieścić logikę” – tabela decyzyjna z odsyłaczami do rozdziałów 4–6. Nie wchodzi głęboko w polityki ani Document Service.
2. **Modelowanie treści.** `schema.json` od środka (na fundamencie): typy pól, walidacje w schemacie, `uid`, `blocks`, enumeracje (i dlaczego nie nazwa `status` – zarezerwowane atrybuty), media. Collection vs single type. Komponenty vs relacje vs dynamic zones – kiedy co (z kosztem w populate i zapytaniach). Relacje: rodzaje, `inversedBy`/`mappedBy`, relacja do `plugin::users-permissions.user`. `documentId` vs `id`, dokument vs wersje (draft/published, locale). Content-Type Builder w dev, a pliki w repo w produkcji (CTB wyłączony w production). Zmiany schematu a dane: zmiana nazwy pola = utrata danych, migracje w `database/migrations` (odesłanie do 13). Typy generowane (`types/generated`) – krótko, szczegóły w 12.
3. **Content API od strony klienta.** REST: odpowiedź v5 (płaska, `documentId`), `populate` (dlaczego domyślnie nic, populate dynamic zone per komponent `on`, populate głębokie i jego koszt), `fields`, `filters` (operatory, `$and/$or`, filtrowanie po relacji), `sort`, paginacja (page vs offset, limity `maxLimit`/`defaultLimit` w `config/api.ts`), `status=draft|published`, `locale`. Budowanie zapytań `qs` po stronie klienta. Tworzenie/aktualizacja relacji (`connect`/`disconnect`/`set`). Oficjalny klient `@strapi/client`. Generowanie specyfikacji OpenAPI (`strapi openapi`). GraphQL: instalacja pluginu, zapytania z `documentId`, konfiguracja (`depthLimit`, `amountLimit`, playground), rozszerzanie schematu (shadow CRUD wyłączanie, własny resolver, polityki/middleware w resolverConfig). Weryfikacja curl-em na danych z seeda.
4. **Trasy, polityki i middleware (rozdział centralny).** Trasy: core router i jego konfiguracja (`only`, `except`, `config` per akcja), trasy własne (`src/api/x/routes/01-custom.ts`, kolejność plików), `auth: false`, prefix. Polityki: czym są (funkcja zwracająca true/false przed kontrolerem, nie modyfikuje odpowiedzi), sygnatura `(policyContext, config, { strapi })`, globalne `global::`, API-scoped, plugin, konfiguracja polityki w trasie, `PolicyError` i własny komunikat, polityka `is-owner` (autor edytuje tylko swoje artykuły) – porządnie, z uwagą na `documentId` i to, że polityka dostaje kontekst przed kontrolerem. Middleware: globalne (`config/middlewares.ts`, kolejność, konfiguracja wbudowanych `strapi::security`/`cors`/`body`), middleware trasy (route-level) i ich różnica, sygnatura `(config, { strapi }) => async (ctx, next)`, kod po `await next()` (modyfikacja odpowiedzi, czas żądania, nagłówki), rate limiting komentarzy, logowanie. Wielka tabela „polityka vs middleware vs middleware Document Service vs kontroler” z przykładami. Kolejność wykonania pokazana logami z uruchomionego projektu. Pułapki: polityka globalna nie działa sama (trzeba ją podpiąć), `is-owner` na `find` (lista) zamiast filtra, middleware Content API nie łapie zmian z panelu admina (most do rozdziału 6). Testy curl dla każdej polityki: 200/403.
5. **Kontrolery, serwisy, walidacja i błędy.** Core controller i serwis: co robią domyślne akcje (find, findOne, create, update, delete), rozszerzanie przez `factories.createCoreController(uid, ({ strapi }) => ({ ... }))`, wywołanie `super`, nadpisanie vs nowa akcja. `validateQuery`, `sanitizeQuery`, `sanitizeOutput`, `sanitizeInput` – dlaczego bez nich wyciekają pola prywatne i relacje, do których rola nie ma dostępu. Cienki kontroler, logika w serwisie; serwis własny (np. `articleService.publishWithReadingTime`). Akcja niestandardowa (np. `GET /articles/:id/related`, `POST /comments/:id/approve`) z trasą. `ctx` w kontrolerze (`ctx.state.user`, `ctx.query`, `ctx.request.body`, `ctx.badRequest` itd.). Błędy: `errors` z `@strapi/utils` (`ApplicationError`, `ValidationError`, `NotFoundError`, `ForbiddenError`), format błędu w odpowiedzi, walidacja wejścia (yup z utils albo zod – co wybrać i dlaczego). Pułapka: zwracanie surowych encji bez sanitizacji.
6. **Document Service, Query Engine i reagowanie na zmiany.** Document Service API: `strapi.documents(uid).findMany/findOne/findFirst/create/update/delete/publish/unpublish/discardDraft/count`, parametry `status`, `locale`, `filters`, `populate`, `fields`, `sort`, paginacja. Kiedy zejść do Query Engine (`strapi.db.query`) – operacje masowe, agregaty, brak warstwy dokumentów, i czego wtedy nie dostajesz (brak middleware DS, brak obsługi draft/publish). Transakcje (`strapi.db.transaction`). Reagowanie na zmiany: lifecycle hooks (`lifecycles.ts`, `beforeCreate`/`afterUpdate`… – działają na poziomie bazy, odpalają się wielokrotnie przy D&P/i18n) vs middleware Document Service (`strapi.documents.use()` w `register`) – zalecany sposób w v5. Przykłady na projekcie: automatyczne `readingTime` i slug, blokada usunięcia kategorii z artykułami, ustawianie `author` z kontekstu. Pokaż na logach, ile razy odpalają się lifecycles przy publikacji, a ile middleware DS. Rozróżnienie: middleware DS łapie też zmiany z panelu admina, w przeciwieństwie do middleware tras. Pułapki: rekurencja (zapis w middleware wywołuje middleware), `afterCreate` z `strapi.documents` w tej samej transakcji, `entityService` jest przestarzały.
7. **Użytkownicy, tokeny i uprawnienia.** Dwa światy: użytkownicy panelu (admin, RBAC – wersja darmowa: role domyślne i własne role) vs użytkownicy aplikacji (users-permissions). Users-permissions: rejestracja, logowanie `/api/auth/local`, JWT – i nowy domyślny tryb sesji z refresh tokenami (`jwtManagement: 'refresh'`, `sessions`, httpOnly) widoczny w `config/plugins.ts` fundamentu: jak działa, endpointy odświeżania i wylogowania, jak to obsłużyć w kliencie; tryb legacy. Role i uprawnienia (Public, Authenticated, własne role), ustawianie uprawnień kodem w `bootstrap`. Rozszerzanie users-permissions: pola użytkownika, `/users/me` z populate, nadpisanie kontrolera/trasy przez `src/extensions/users-permissions/strapi-server.ts`, register allowed fields. Providerzy OAuth (konfiguracja jednego, np. GitHub – opis, wynik przykładowy). Reset hasła i potwierdzanie e-maila (krótko, odesłanie do e-maila w 8). API tokens (read-only, full access, custom; kiedy zamiast JWT – serwer-serwer, SSR). Admin tokens i MCP (odesłanie do 12). Wzorce autoryzacji danych: ownership (odesłanie do 4), filtrowanie listy po użytkowniku w kontrolerze/middleware DS. Pułapka: `populate=*` na relacji do usera i wyciek pól.
8. **Funkcje wbudowane.** Draft & publish w v5 (dwie wersje dokumentu, `status`, `publishedAt`, publish/unpublish/discard z API, co widzi Public). i18n: włączenie na typie i polach, `locale` w REST i Document Service, tworzenie tłumaczeń, brak `locale=all`. Media Library: upload przez REST (`/api/upload`, upload a potem powiązanie – brak uploadu przy tworzeniu wpisu w v5), formaty/breakpointy, `allowedTypes`/`deniedTypes` z fundamentu, provider lokalny vs S3-kompatybilny (MinIO/R2/S3; konfiguracja + CSP w `strapi::security`, wynik przykładowy). E-mail: provider nodemailer (SMTP), `strapi.plugin('email').service('email').send`, szablony (np. powiadomienie autora o nowym komentarzu; w dev np. Mailpit w Dockerze albo wynik przykładowy). Webhooki: konfiguracja w panelu, zdarzenia (`entry.publish` itd.), payload, nagłówki z sekretem, weryfikacja po stronie odbiorcy (odesłanie do 11). Cron: `config/cron-tasks.ts`, `server.cron.enabled`, przykład – zaplanowana publikacja albo czyszczenie odrzuconych komentarzy. Preview (darmowa część: konfiguracja `preview` w `config/admin.ts`, odesłanie do 11).
9. **Własny plugin.** Kiedy plugin, a kiedy kod w `src/api` (współdzielenie między projektami, izolacja). Plugin SDK (`npx @strapi/sdk-plugin init`), struktura (server/admin), `watch:link` vs lokalny plugin w `src/plugins`, rejestracja w `config/plugins.ts`. Strona serwerowa: content-type pluginu, serwisy, kontrolery, trasy content-api vs admin, polityki i middleware pluginu, konfiguracja z walidacją, `register/bootstrap`. Przykład: plugin „reading-stats” albo „comment-moderation” (kolejka komentarzy do moderacji z endpointem admina). Strona admina: rejestracja w menu, strona ustawień, `useFetchClient`, uprawnienia RBAC pluginu. Rozszerzanie wbudowanych pluginów (`src/extensions`). Rozszerzanie serwera MCP Strapi o narzędzie pluginu (`strapi.ai.mcp`, krótko, jeśli dostępne w darmowej wersji). Publikacja na npm (krótko).
10. **Panel admina i custom fields.** `src/admin/app.tsx` (konfiguracja: locale, tłumaczenia, motyw, logo), rozszerzenia przez `register`/`bootstrap` admina, injection zones (np. przycisk „podgląd na stronie” w edycji artykułu), Content Manager APIs, homepage widgets, własny WYSIWYG (krótko). Custom field: rejestracja na serwerze i w adminie (np. pole „kolor kategorii” albo „licznik znaków SEO”), komponent React z Design System. Bundler (vite), `src/admin/vite.config.ts`. Budowanie i hostowanie admina osobno (`serveAdminPanel`, krótko). Weryfikacja: `npm run build` przechodzi; zrzutów ekranu nie robimy, opis zachowania w prozie.
11. **Integracja z frontendem.** Next.js (App Router) jako główny przykład, Nuxt jako różnice w ramce. Pobieranie danych na serwerze z API tokenem (read-only) vs w przeglądarce bez tokena, `@strapi/client` vs fetch + `qs`, typy odpowiedzi (generowanie typów dla frontu – realistyczne podejście). Cache i rewalidacja: webhook `entry.publish` → route handler z weryfikacją sekretu → `revalidateTag`. Logowanie użytkowników aplikacji (users-permissions + refresh tokeny z rozdziału 7, httpOnly cookie po stronie Next). Podgląd szkiców (Preview: `status=draft`, draft mode w Next, konfiguracja `preview` w adminie). CORS w `strapi::cors`. Obrazy (URL-e z media, `next/image` remotePatterns). Kod frontu w `examples/11-frontend/` jako minimalny projekt albo pliki do wklejenia; weryfikacja przynajmniej `tsc` i curl, pełne uruchomienie Next jeśli rozsądne.
12. **TypeScript, testy i narzędzia AI.** TypeScript: `strapi ts:generate-types`, typy `Data.ContentType<'api::article.article'>`, `Modules.Documents`, `Core.Strapi`, typowanie kontrolerów/serwisów/polityk, `autogenerate`. Testy: podejście z dokumentacji (Jest/Vitest + supertest, instancja Strapi w teście na SQLite w pamięci/tmp), test polityki `is-owner` i middleware rate limit (na kodzie z rozdziału 4), test serwisu, uruchomienie w CI. Narzędzia AI dla dewelopera: Docs MCP (`https://strapi-docs.mcp.kapa.ai`, konfiguracja w Claude Code), `llms.txt`, wbudowany serwer MCP Strapi (`mcp: { enabled: true }` w `config/server.ts`, admin tokens, co potrafi, bezpieczeństwo – tylko jeśli działa w wersji darmowej; zweryfikuj uruchamiając).
13. **Produkcja self-hosted.** Dockerfile (multi-stage, `npm ci`, `npm run build`, `NODE_ENV=production`, użytkownik non-root) i docker-compose z Postgresem (healthcheck, wolumeny `public/uploads`), konfiguracja `config/env/production`, zmienne wymagane (APP_KEYS, secrets – skąd i jak rotować), `server.url` i `proxy` za reverse proxy (Traefik/Caddy/Nginx; wzmianka o Traefik, bo autor go używa), CTB wyłączony w produkcji – zmiany schematu tylko przez repo. Dane: `strapi export/import/transfer` (transfer między instancjami z tokenem transferu), backup Postgresa, migracje w `database/migrations` (kiedy potrzebne), transakcje migracji. Aktualizacje: `@strapi/upgrade` (codemody, minor/major), cadence wydań (tygodniowe minory), testowanie aktualizacji. Wydajność: populate, indeksy, paginacja, cache odpowiedzi (np. middleware cache albo cache na froncie), logi. Bezpieczeństwo: checklista (CORS, CSP, rate limit auth, `deniedTypes`, uprawnienia Public, wyłączenie rejestracji, admin pod osobną ścieżką/IP). Weryfikacja: `docker build` i `docker compose up` z Postgresem lokalnie, curl na `/_health` i API.
